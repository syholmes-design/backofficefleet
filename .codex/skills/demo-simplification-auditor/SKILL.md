# Demo Simplification Auditor

Use this skill when the demo is too complex, too broad, too dense, or at risk of repeating the old BOF experience.

## Purpose

Cut complexity so the demo feels guided, complete, robust, and show-ready.

## When To Use

- Too many screens
- Too many buttons
- Confusing labels
- Duplicate pages
- Unnecessary dashboards
- Overbuilt workflows
- Weak demo/document surfaces
- Thin pages created by oversimplification
- Missing proof, status, owner, consequence, or next action

## Procedure

1. Identify the intended demo path.
2. List every visible screen/action competing with that path.
3. Classify each item as required, simplify, hide, optional, or out of scope.
4. Preserve the old demo's strongest credibility signals: data-backed context, document proof, operational consequences, persona paths, and ownership.
5. Prefer hiding, merging, or renaming before adding features.
6. If hiding a complex surface weakens the story, replace it with a smaller polished proof point.
7. Stop once the path is show-ready.

## Checks

- Can the owner show the demo without apologizing?
- Does every visible primary action help the walkthrough?
- Are weak or unfinished areas hidden?
- Are labels obvious?
- Is the path shorter than the old reference app?
- Does the path still feel as robust and detailed as the original demo?
- Did simplification remove confusion without removing credibility?

## Output Format

```markdown
## Demo Simplification Audit

Demo path:
Required before demo:
Simplify before demo:
Hide from demo:
Optional later:
Proof/detail to preserve:
Final demo path:
```

## Safety Boundaries

- Do not delete files unless explicitly asked.
- Do not expand the demo to solve a complexity issue.
- Do not touch `bof-web-Original`.
- Do not make the demo bare, generic, or underbuilt in the name of simplicity.
