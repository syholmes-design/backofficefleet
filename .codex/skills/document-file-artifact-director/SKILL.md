# Document File Artifact Director

Use this project-local skill when BOF demo documents need to look and behave like real document files: DOCX/PDF-style paperwork, rendered page artifacts, scan/photo assets, or generated license/CDL-style images instead of HTML cards embedded in the UI.

This role exists because the client is not satisfied by complete fields inside a nice app panel. Important paperwork should feel like a file the fleet owner opened, reviewed, downloaded, or received, with the app UI acting as a viewer around the document rather than the document itself.

## Purpose

Own the file-artifact standard for BOF demo paperwork:

- primary documents should be DOCX/PDF-style artifacts or rendered page images where appropriate
- the app should show a document viewer, not use the website/app template as the document body
- generated driver-license/CDL-style images should be used for license surfaces
- documents should have realistic per-document layouts, page proportions, signatures/stamps/fields, and file names
- artifacts should be static, compressed, inspectable, and linked from the demo record

The goal is not production document automation. The goal is a client-presentable static demo where paperwork looks like paperwork.

## When To Use

- The user says documents should be DOCX/PDF, real files, downloads, scans, or not HTML.
- The user says driver licenses should be ChatGPT/image-generated.
- Driver licenses/CDLs, medical cards, MVRs, employment forms, BOLs, PODs, rate confirmations, insurance certificates, W-9/I-9-style forms, prior employer inquiries, road tests, safety acknowledgements, settlement paperwork, or carrier packets are being created or reviewed.
- A document currently appears as an HTML card, table, or app panel instead of a file artifact.
- The demo needs a document viewer with realistic pages, thumbnails, file metadata, or download/open actions.
- A checklist requires client-facing document realism and the artifact must survive close inspection.

## Procedure

1. Confirm `Website` is the active target and `bof-web-Original` is reference-only.
2. Inventory the required documents and classify each:
   - `file-artifact-required`: should be DOCX/PDF-style, rendered PDF/image page, or downloadable static file.
   - `generated-image-required`: driver's license/CDL, ID-style card, scan/photo evidence, seal/dock/cargo photo.
   - `viewer-metadata-only`: surrounding app UI can be HTML, but the primary document body cannot be an app card.
3. For each important driver document, require a realistic file destination or viewer state, not just a checklist label.
4. For driver licenses/CDLs, require generated image artifacts:
   - use synthetic people/details only
   - do not reuse driver faces
   - match driver name/gender presentation
   - make the image professional and license-like
   - keep it fictional, non-official, and non-scannable
5. For DOCX/PDF-style documents:
   - create document-specific pages or static rendered assets
   - use realistic page dimensions and file names
   - include synthetic dates, parties, document numbers, reviewers, signatures, stamps, and status fields
   - avoid `Masked`, `Private value`, `On file`, `TBD`, `sample`, and placeholder values when complete fictional values are safe
6. Present files through a viewer:
   - app chrome around the document
   - large readable page
   - file name, type, owner, status, source, and related record
   - open/download-style controls that work or are clearly represented
7. Keep generated/source files static under `Website/assets/` or another deployable static folder.
8. Compress image artifacts before closeout when appropriate.
9. Render and visually verify important DOCX/PDF/image artifacts before accepting them.
10. Keep buyer-facing language product-safe. Do not call artifacts `mock`, `fake`, `static`, `generated by ChatGPT`, or `demo-only` in the UI.

## Checks

- Is the primary document body a file-like artifact rather than the app/site UI template?
- Does the document look credible when enlarged?
- Are driver licenses/CDLs generated image artifacts, not HTML tables?
- Are generated license-style images fictional, non-official, non-scannable, and safe?
- Are document pages specific to their type rather than one reused template?
- Are file names, dates, parties, signatures, document numbers, and statuses complete and consistent?
- Are records linked to actual static artifacts or complete viewer states?
- Are artifacts readable on desktop and mobile?
- Are assets compressed and stored in the deployable `Website` folder?
- Is no real private data, real credential, credential barcode, government seal, or production claim exposed?

## Failure Modes

- Treating an HTML card/table as a real document because it has filled-out fields.
- Making a license as plain HTML instead of a generated image artifact.
- Reusing one generic form layout for unrelated documents.
- Leaving document checklist items clickable but not backed by an artifact or viewer.
- Generating license-style images that look like exact real government credentials or include scannable codes.
- Using real private data, real document numbers, or real faces without authorization.
- Adding heavy document-generation infrastructure when static artifacts would satisfy the demo.

## Safety Boundaries

- Do not edit `bof-web-Original`.
- Do not add React, Next.js, TypeScript, npm packages, server routes, databases, upload systems, auth, credentials, `.env`, API calls, webhooks, or production document automation.
- Do not create or imply real legal, medical, tax, insurance, government, CDL, identity, bank, or compliance documents.
- Do not create scannable barcodes, machine-readable zones, real state seals, real license numbers, real DOT/MC/policy numbers, or artifacts that could be mistaken for usable credentials.
- Do not use real private/reference data.
- Do not expose internal generation or build notes in buyer-facing UI.
