Build the AscendTMS Partner Integration Layer for BackOfficeFleet
AscendTMS is now a confirmed partner path for BackOfficeFleet, so we need to build a Phase 1 integration that proves the operating workflow before we attempt a deeper API connection. The first goal is to show that AscendTMS manages the TMS/load workflow while BOF controls readiness, compliance, documents, exceptions, audit trail, and release decisions.
Primary Objective
Build a self-contained AscendTMS partner integration demo inside the existing BackOfficeFleet site/repo.
This should not be a real API integration yet. It should be an API-ready architecture using mock AscendTMS data, clean adapter files, synthetic records, and UI screens that can later be connected to AscendTMS API credentials, CSV import, webhook events, or partner sandbox data.
The implementation must preserve BOF’s existing driver database, document vault, compliance logic, driver records, and readiness rules. AscendTMS should be treated as the source system for load/TMS activity. BOF should remain the source system for driver compliance, document readiness, release decisions, audit records, exception management, and settlement hold logic.

Release Decision Rules
Use these basic rules:
Ready to Release:
Driver matched
Driver compliance clear
Carrier packet clear
Required pre-trip documents present
No active blocking exceptions
Release With Condition:
No legal/compliance blocker
Minor document still pending but not yet required
Example: POD not yet uploaded before delivery
Next action is clear
Owner is assigned
Hold — Action Required:
Driver unmatched
Driver compliance blocked
Expired CDL/medical/MVR
Missing required pre-trip document
Carrier packet blocked
Insurance or authority missing/expired
Critical exception unresolved
